AgentHub Memory

后端对会话记忆的保存方式

AgentHub 的会话记忆不是单一字段，而是由原始消息、可检索 context item、向量 embedding、长期摘要和每次 run 的 context snapshot 共同组成。数据库是事实源，内存只保存短期摘要缓冲和下游连接状态。

1. 记忆层次

原始事实

messages、agent_events、artifacts、file_changes 保存可回放的事实。

检索条目

context_items 把消息、文件变更、artifact 转成统一文本。

向量索引

context_embeddings 保存 context item 的 embedding，用于相似召回。

运行快照

context_snapshots 固化每次 run 当时选中的 pins、recent、retrieved 和 summary。

表/结构保存内容是否持久化用途
messages用户消息和完成后的 assistant 消息。是聊天主记录、刷新恢复、recent 来源。
context_items可进入记忆系统的文本条目，带 kind、importance、pinned。是pin、召回、上下文预算选择。
context_embeddings每个 context item 在指定 embedding model 下的向量。是pgvector 相似召回。
long_term_summaries短期 buffer 压缩后的摘要链。是bootstrap memory.summary 来源。
context_snapshots一次 run 启动前选择出来的上下文快照。是审计、回放、传给云 Agent。
shortTermBuffers内存 Map，按 session 收集新增 context item 文本。否达到阈值后压缩为长期摘要。

2. 写入时机

2.1 用户消息

  1. 用户调用 POST /api/sessions/:id/messages。
  2. 后端创建 messages(role=user)，保存原始 contentText 和 contentJson.mentionedAgentIds。
  3. 调用 recordContextItem，写入 context_items(kind=message, sourceType=message)，importance 为 20。
  4. 尝试为该 context item 生成 embedding。
  5. 把 message: 用户文本 加入 session 的短期摘要 buffer。

2.2 云 Agent 完成消息

message.delta 只进入内存 buffer 和事件流；message.completed 才创建最终 assistant message。

  1. 后端从 speaker 对应的内存 buffer 取完整文本，或使用 payload 文本。
  2. 创建 messages(role=assistant, agentId=speakerId, runId)。
  3. 更新 agent_runs.assistantMessageId。
  4. 写入 context_items(kind=message, importance=10)，metadata 包含 runId 和 agentId。

2.3 文件变更和 artifact

事件派生事实派生记忆
file.change写入 file_changes。写入 context_items(kind=file_change, importance=40)，文本是 changeType、path、patch 或 afterContent 的前 8000 字符。
artifact.upsert创建/更新 artifacts。当前 upsert 本身不写 context item。
artifact.complete把 artifact 标记为 final。写入 context_items(kind=artifact, importance=30)，文本是 title 加 textContent 或 storageUri 的前 8000 字符。

3. Context Snapshot 构造

每次发送用户消息都会在启动云 Agent 前调用 buildSnapshot。该方法会先创建 context_update_jobs(reason=build_snapshot, status=running)，完成后把 job 更新为 completed。

3.1 数据来源

snapshot 区块来源排序/限制
pinscontext_items.pinned = true按 importance 降序、updatedAt 降序，最多 20 条。
recent最近 messages按 createdAt 降序取 24 条，再反转为时间正序。
retrievedrecallByPgvector 或词法 fallback默认 CONTEXT_RETRIEVAL_LIMIT=8。
summarylong_term_summaries按 seq 升序拼接。
mentionedAgents本次消息解析出的 Agent 实例保存 {id, name}。

3.2 预算策略

配置默认值用途
CONTEXT_TOKEN_BUDGET9000总上下文预算。
CONTEXT_RECENT_TOKEN_BUDGET4800recent 消息预算。
CONTEXT_RETRIEVAL_LIMIT8召回条目数量。

选择顺序是 pins、recent、retrieved。每个 item 如果 id 已选过就跳过；如果加入后超过该区块预算也跳过。summary token 会加入 snapshot 的 tokenCount。

4. 长期摘要怎么保存

每次 recordContextItem 都会把文本追加到进程内 shortTermBuffers。当满足任一阈值时，后端调用摘要模型压缩并写入 long_term_summaries。

阈值/配置当前值说明
SHORT_TERM_EVENT_LIMIT20buffer 中事件数达到 20 条触发压缩。
SHORT_TERM_TOKEN_LIMIT2000buffer token 估算达到 2000 触发压缩。
CONTEXT_SUMMARY_MODELdeepseek-chat摘要模型名，可用环境变量覆盖。
SUMMARY_API_KEY可选没有 key 或 base URL 时，直接截断前 4000 字符作为摘要。

写入长期摘要时，seq 是当前 session 最大 seq 加 1。写入成功后，内存 buffer 会清空。

5. 向量召回怎么保存和使用

  1. recordContextItem 创建 context item 后调用 persistEmbedding。
  2. createEmbedding 读取 OPENAI_API_KEY 或 OPENAI_COMPATIBLE_API_KEY，以及 OPENAI_COMPATIBLE_BASE_URL 或 OPENAI_BASE_URL。
  3. 请求 /embeddings，默认模型为 text-embedding-3-small，文本最多取前 12000 字符。
  4. 成功后用原始 SQL 写入 context_embeddings，冲突键为 (context_item_id, model)。
  5. 构造 snapshot 时，先尝试 pgvector <=> 相似度排序；失败时降级为关键词词法匹配。
容错策略

embedding 失败或 pgvector 扩展不可用不会阻塞消息保存；后端会降级到词法召回或返回空 retrieved。

6. Pin 机制

前端调用 POST /api/sessions/:sessionId/messages/:messageId/pin 切换消息 pin 状态。

  1. 后端更新 messages.isPinned。
  2. 如果已有对应 context_items(sourceType=message, sourceId=messageId)，同步更新 pinned。
  3. 如果没有 context item，则创建一个。pin=true 时 kind 为 manual_pin、importance 为 100；否则 kind 为 message。
  4. 写入 context.updated 事件，payload 包含 messageId 和 pinned。

7. 当前边界

  • 短期摘要 buffer 是进程内 Map，后端重启会丢失尚未压缩的短期 buffer，但已写入数据库的 messages/context_items 不会丢。
  • tokenCount 是按 Math.ceil(text.length / 4) 的粗略估算，不是模型 tokenizer 精确值。
  • context_snapshots.promptText 会保存渲染后的上下文文本，但当前发送云 Agent 的 bootstrap payload 不直接发送 promptText。
  • context_update_jobs 当前主要记录 build snapshot 的运行状态，不是后台队列。
  • 长期摘要由 long_term_summaries 保存；当前 schema 没有旧设计稿里的 session_contexts 表。
