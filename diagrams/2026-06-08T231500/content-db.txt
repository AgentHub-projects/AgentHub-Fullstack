<h2>设计思路</h2><p>AgentHub 的数据库设计围绕<strong>会话级上下文记忆</strong>这一核心场景展开。与传统知识库（全局文档索引）不同，本系统将"知识"限定在单个会话范围内，每条 Agent 产出都即时转化为可检索的上下文向量。核心表围绕三条主线：</p><ul><li><b>会话主体线</b>：Session → AgentRun → Message/AgentEvent，记录完整的对话和运行历史</li><li><b>上下文记忆线</b>：ContextItem → ContextEmbedding → ContextSnapshot → SessionMemory，实现语义检索和结构化记忆</li><li><b>产物管理线</b>：Artifact → FileChange，管理 Agent 产出的文件和代码变更</li></ul><hr/><h2>架构决策</h2><h3>为什么选择 PostgreSQL + pgvector 而不是专用向量数据库？</h3><p><b>决策</b>：使用 PostgreSQL 的 pgvector 扩展存储嵌入向量，而非部署独立的 Milvus/Qdrant/Pinecone。</p><p><b>理由</b>：</p><ul><li><b>减少运维复杂度</b>：项目已依赖 PostgreSQL，增加一个独立向量数据库会引入额外的部署、监控、备份成本。对于会话级（非海量文档级）的检索需求，pgvector 完全够用</li><li><b>事务一致性</b>：ContextItem 和 ContextEmbedding 在同一事务中写入，无需分布式事务。如果向量写入失败，可通过 ON CONFLICT DO UPDATE 幂等重试</li><li><b>JOIN 查询便利</b>：向量检索需要关联 ContextItem 获取元数据（kind、importance、pinned），在同一数据库中一条 SQL 即可完成</li></ul><p><b>更优解</b>：如果未来需要跨会话全局知识库（百万级以上文档），可迁移到 pgvector 的 IVFFlat/HNSW 索引，或引入 Milvus 作为二级向量存储。当前阶段不采用，因为跨会话知识库的需求尚未明确，过早优化会增加系统复杂度。</p><h3>为什么使用 Prisma ORM？</h3><p>Prisma 提供类型安全的数据库操作，与 NestJS + TypeScript 技术栈深度集成。但 pgvector 的 vector 类型不被 Prisma 原生支持，因此使用 Unsupported("vector(1536)") 转义 + $queryRawUnsafe 执行原始 SQL。这是 TypeScript 生态的常见取舍——牺牲少部分 ORM 的完整性，换取 95% 查询的类型安全。</p><hr/><h2>数值参数分析</h2><table><tr><td><p>参数</p></td><td><p>取值</p></td><td><p>依据</p></td></tr><tr><td><p>embedding dims</p></td><td><p>1536</p></td><td><p>text-embedding-3-small 的标准输出维度，与 pinned、kind），已提取为独立列</p></td></tr></table><hr/><h2>与市面平台对比</h2><table><tr><td><p>维度</p></td><td><p>AgentHub</p></td><td><p>LangChain/LlamaIndex</p></td><td><p>Dify/Coze</p></td></tr><tr><td><p>向量存储</p></td><td><p>pgvector，会话级</p></td><td><p>多后端可插拔</p></td><td><p>内置向量数据库</p></td></tr><tr><td><p>记忆粒度</p></td><td><p>每事件即索引</p></td><td><p>文档级分块</p></td><td><p>知识库级</p></td></tr><tr><td><p>结构化记忆</p></td><td><p>LLM
