<hr/><h2>一小时空闲断连的设计缘由</h2><h3>核心决策</h3><p>DownstreamOrchestratorService 在 session 无活跃 run 且无前端订阅时，等待 IDLE_TIMEOUT_SECONDS（3600s = 1小时）后断开下游 WebSocket 连接。</p><h3>为什么是 1 小时？</h3><p><b>根因：大模型 KV Cache 的 TTL 语义</b></p><p>主流 LLM 推理引擎（vLLM、SGLang 等）对 KV Cache 的默认 TTL 通常在 5 分钟到 1 小时之间。KV Cache 缓存了 prefix 部分的注意力计算结果，使得后续请求如果共享相同 prefix，可以跳过重复计算。</p><p>具体到 AgentHub 的场景：</p><ul><li><b>1 小时内重连</b>：下游 Claude Code / OpenCode 实例仍在运行，其内部可能仍持有 LLM 的 KV Cache（或可通过 session/load 恢复）。此时发送新 prompt，如果系统 prompt 和上下文快照的 prefix 部分不变，推理引擎可以直接复用缓存的 KV 状态，<b>不会产生额外的 prefill 计算成本</b>。</li><li><b>超过 1 小时后重连</b>：KV Cache 几乎必然已过期。重新发送 prompt 时，即使 prefix 完全不变，推理引擎也需要重新计算整个 prefix 的注意力矩阵（prefill），产生额外的 GPU 计算和 API 费用。此时是否保持连接已经没有成本优势——<b>不如断开重建，让系统 clean start</b>。</li></ul><h3>1 小时内静默维护的策略</h3><p>在 1 小时窗口内，AgentHub 不主动断开下游连接。Claude Code / OpenCode 实例保持静默运行，通过 ACP 协议维持心跳。好处：</p><ul><li><b>用户连续对话体验无延迟</b>：新消息到达时，下游连接已存在，直接发送 session/prompt，跳过了 initialize + session/load 握手（约 1-3 秒延迟）</li><li><b>incremental 模式可复用</b>：如果 session 保持活跃（Redis key 未过期），后续消息以 incremental 模式发送，跳过完整的上下文快照构建</li></ul><h3>空闲检测机制</h3><p>断连不是硬超时（1 小时后无条件断开），而是<b>空闲检测</b>：</p><ul><li>每次发送 prompt 或收到下游事件时，刷新 Redis session:active key 的 TTL（重置为 3600s）</li><li>定时器每 60s 检查：无活跃 run 且无前端 WebSocket 订阅者<b>且</b> Redis key 已过期 → 才断开</li><li>这意味着<b>用户持续对话时连接永远不会断开</b>，只有真正空闲 1 小时才会清理</li></ul><h3>与 KV Cache 的精确配合</h3><p>这个设计形成了一个优雅的配合：</p><ul><li>如果用户在 1 小时内回来继续对话 → 连接仍在（或可秒级恢复），KV Cache 可能仍有效，zero-cost context restore</li><li>如果用户超过 1 小时才回来 → 主动断开旧连接，创建新连接，bootstrap 模式重建完整上下文快照。此时 KV Cache 已过期，断开是零损失决策</li></ul><h3>为什么不用更短或更长的超时？</h3><table><colgroup><col/><col/><col/></colgroup><tbody><tr><td><p><b>方案</b></p></td><td><p><b>优点</b></p></td><td><p><b>缺点</b></p></td></tr><tr><td><p>5 分钟</p></td><td><p>节省下游进程资源</p></td><td><p>用户短暂离开（喝水、查资料）就断连，频繁重建连接和上下文快照，延迟和成本双高</p></td></tr><tr><td><p>24 小时</p></td><td><p>几乎不断连</p></td><td><p>KV Cache 早已过期（超过 1 小时后 cache miss 是确定性事件），保持连接是纯资源浪费。下游 Claude Code 进程空闲 24 小时占用内存</p></td></tr><tr><td><p><b>1 小时（选择）</b></p></td><td><p>对齐 KV Cache TTL 上限</p></td><td><p>在"避免重复 prefill"和"节省连接资源"之间取得最优平衡</p></td></tr></tbody></table>
