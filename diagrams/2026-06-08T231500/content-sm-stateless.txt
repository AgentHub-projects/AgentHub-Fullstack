<hr/><h2>为什么设计 Session Memory：让 Agent 实例可以无状态重启</h2><h3>问题背景</h3><p>AgentHub 的下游 Agent（Claude Code CLI、OpenCode 等）是<b>有状态进程</b>——它们在内存中维护对话历史、文件状态、工具调用上下文。但这种状态是脆弱的：</p><ul><li>进程崩溃 / OOM → 状态全部丢失</li><li>部署更新 → 进程重启 → 状态丢失</li><li>空闲超时断开 → 见上文 1 小时断连策略 → 状态丢失</li><li>负载均衡 / 多实例 → 不同请求可能路由到不同进程</li></ul><p>如果每次 Agent 进程重启后，都从零开始（忘记之前做过什么、改过哪些文件、遇到过什么错误），用户需要不断重复告知上下文，体验极差。</p><h3>Session Memory 的解决方案</h3><p>Session Memory 将 Agent 实例的<b>关键工作状态外化到数据库</b>，使得 Agent 进程可以随时重启并从数据库恢复上下文：</p><ul><li><b>无状态重启</b>：Agent 进程重启后，bootstrap 模式的 ContextSnapshot 自动包含 SessionMemory 的文本摘要。Agent 在 prompt 中读到"之前做了 X，改了文件 Y，遇到了错误 Z"，就像从未断过一样继续工作</li><li><b>跨实例共享</b>：群聊模式下，多个 Agent 实例可以通过 SessionMemory 了解彼此的产出（files 字段中的文件变更记录），实现隐式协作</li><li><b>可审计</b>：SessionMemory 持久化在 DB 中，可以查询一个 session 的完整工作历程（workLog）、所有涉及文件（files）、所有错误及解决状态（errors）</li></ul><h3>为什么设计成结构化 JSON 而非纯文本？</h3><p>纯文本总结（如"之前修改了 login.ts 和 api.ts，遇到了一个 404 错误"）在信息密度和可操作性上都远不如结构化 JSON：</p><table><colgroup><col/><col/><col/></colgroup><tbody><tr><td><p><b>字段</b></p></td><td><p><b>设计的意图</b></p></td><td><p><b>纯文本的缺陷</b></p></td></tr><tr><td><p>title</p></td><td><p>一句话概括当前任务。用于上下文快照的标题行，让 Agent 快速理解"我们在做什么"</p></td><td><p>纯文本中难以识别"这句话是标题还是正文"</p></td></tr><tr><td><p>status</p></td><td><p>任务状态（进行中 / 已完成 / 阻塞）。Agent 重启后可以判断是否需要继续之前的工作</p></td><td><p>纯文本不会显式标注状态，Agent 需要推理才能判断</p></td></tr><tr><td><p>files</p></td><td><p>涉及的文件列表，含 path、changeType、description。支持按 path 去重合并（同一文件多次修改只保留最新状态），让 Agent 知道"哪些文件是我们正在改的"</p></td><td><p>文件列表散落在文本各处，无法按 path 高效去重，也无法结构化查询</p></td></tr><tr><td><p>errors</p></td><td><p>遇到的错误列表，含 message、solution、resolved 标记。支持按 message 去重合并，Agent 重启后可以知道"之前遇到过哪些错误、解决了没有"</p></td><td><p>错误信息可能与多轮对话混淆，resolved 状态难以追踪</p></td></tr><tr><td><p>lessons</p></td><td><p>从本轮工作中提炼的经验教训。跨轮次积累，帮助 Agent 避免重复犯错</p></td><td><p>经验教训与对话混在一起，下次启动时可能被截断或丢失</p></td></tr><tr><td><p>workLog</p></td><td><p>工作日志时间线，每条含 timestamp + summary。新增条目追加到前面，保留最近 20 条。提供时间维度的上下文</p></td><td><p>无法按时间排序和裁剪，旧工作可能挤占新工作的 token 预算</p></td></tr></tbody></table><h3>合并策略的精心设计</h3><p>SessionMemory 的 upsert 不是简单覆盖，而是<b>字段级语义合并</b>：</p><ul><li><b>title / status / lessons：覆盖</b>——最新状态应该替换旧状态</li><li><b>files：按 path 去重合并</b>——同一文件被多次修改时，保留最新的描述。这避免了 files 数组无限膨胀（如 login.ts 被改了 50 次，只保留 1 条）</li><li><b>errors：按 message 去重合并</b>——同一个错误（如 "404 on /api/login"）不管出现多少次，只保留 1 条。但通过 resolved 字段标记最新解决状态</li><li><b>workLog：追加新条目，保留最近 20 条</b>——时间线语义，旧的不删但限制上限</li></ul><h3>延伸价值</h3><p>这个设计不仅服务于"无状态重启"，还天然支持了：</p><ul><li><b>会话导出</b>：SessionMemory 可以直接导出为 Markdown 工作记录</li><li><b>知识沉淀</b>：跨会话汇总 lessons 和 errors，可以形成项目级的经验库（当前未实现，但数据结构已预留）</li><li><b>调试诊断</b>：workLog 时间线可以帮助开发者（人类）理解 Agent 在某个 session 中到底做了什么</li></ul>
