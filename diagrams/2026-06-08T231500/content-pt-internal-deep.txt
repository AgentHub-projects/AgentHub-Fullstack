<hr/><h2>内部 Prompt 组装：从函数签名到最终文本的完整追踪</h2><h3>组装入口：buildPromptInput()</h3><p>位置：downstream-orchestrator.service.ts:802-843。先看它的输入：</p><ul><li>input.sessionId / input.runId / input.userMessageId：标识信息</li><li>input.promptText：用户的原始输入文本</li><li>input.messageContext：当前消息附带的结构化上下文（附件引用、链接预览的 JSON）</li><li>input.orchestrator / input.mentionedAgents：Agent 身份信息</li><li>input.context：HubContextSnapshotDto | null | undefined——这就是前面 dispatchPrompt 决策的结果：bootstrap 时传入完整快照，incremental 时为 null</li></ul><p>它的输出是 ACP session/prompt 的参数对象，核心字段是 prompt: [{ type: "text", text: promptText }]。</p><p>promptText 从哪来？不是直接复制 input.promptText，而是通过 renderAgentGatewayPrompt() 包装后的结果。</p><p>关键分支：</p><ul><li><code>const promptMode = bootstrap ? "bootstrap" : "incremental";</code></li><li><code>const agents = bootstrap ? await this.loadSessionAgentBriefs(...) : [];</code>——只有 bootstrap 时才查数据库加载可用 Agent 列表</li><li><code>const promptText = renderAgentGatewayPrompt({ promptText, promptMode, contextText: bootstrap ? input.context?.promptText : undefined, messageContext, mentionedAgents, agents });</code>——incremental 时 contextText 和 agents 都不传</li></ul><h3>renderAgentGatewayPrompt() 逐行拆解</h3><p>这个函数（downstream-orchestrator.service.ts:890-912）接收六个参数，返回一个字符串。内部用一个 sections 数组收集各个段落，最后用 \n\n 连接，过滤掉空字符串。</p><p><b>Section 1: System 层（必定存在）</b></p><p><code>"# AgentHub 任务分派 (${input.promptMode})"</code> + <code>"请基于以下会话上下文和用户请求完成当前任务。"</code></p><p>这一层的设计意图是<b>告诉下游 Agent 它的角色和运行模式</b>。Markdown 的一级标题 # 在 LLM 的注意力机制中会被赋予高权重。promptMode 标注 bootrap 还是 incremental 不是给人看的——下游 Agent 可以根据这个标记调整行为（bootstrap 时认真读完整上下文，incremental 时只需关注当前消息）。</p><p><b>Section 2: Context 层（仅在 bootstrap 时存在）</b></p><p><code>input.contextText ? "## 会话上下文\n${input.contextText}" : ""</code></p><p>contextText 是什么？它是 ContextSnapshot.promptText，也就是 renderContextPrompt() 的输出。需要注意的是，这个字符串可能很长——置顶项、最近 24 条消息、向量检索结果、SessionMemory 摘要的拼接。它的内容来自另一个渲染函数，后面单独分析。</p><p>incremental 时这一整段是空字符串，被 sections.filter() 过滤掉。最终发给下游的 Prompt 里根本没有 "## 会话上下文" 这个段落。</p><p><b>Section 3: Agent 层（仅在 bootstrap 且有 @ 提及或可用 Worker 时存在）</b></p><p>两部分独立判断：</p><ul><li>mentionedAgents 不为空 → 渲染 "## 提及的 Agent" 列表，格式为 "- agentName (agentId)"。这是用户在当前消息中 @ 的 Agent</li><li>agents 不为空 → 渲染 "## 可用 Worker Agent" 列表，格式为 "- agentId: description"。这是 session 中所有的非 orchestrator Agent</li></ul><p>两个列表的用意不同：mentionedAgents 告诉 orchestrator "用户想找谁帮忙"——这是用户意图。available agents 告诉 orchestrator "你有哪些手下可以调遣"——这是能力边界。Orchestrator 需要综合两者做任务分派。</p><p><b>Section 4: Message Context 层（有附件/引用时存在）</b></p><p><code>messageContextPrompt(input.messageContext)</code> 将 messageContext JSON 序列化为格式化的 JSON 文本，限制 12000 字符。这个 section 独立于 ContextSnapshot——不是历史上下文，而是当前消息的结构化元数据。无论 bootstrap 还是 incremental 都会包含。</p><p><b>Section 5: Message 层（必定存在）</b></p><p><code>"## 当前用户请求\n${input.promptText}"</code></p><p>用户的原始输入，不做任何加工。</p><h3>ContextSnapshot.promptText 的来源：renderContextPrompt()</h3><p>位置：context.service.ts:560-584。这个函数将 ContextSnapshotPayload（一个结构化对象）渲染为 Markdown 文本。</p><p>输出顺序：</p><ol><li><b>"你正在恢复一个已有的 AgentHub 会话。请先阅读以下上下文再执行操作。"</b>——硬编码的开场白。这句话非常关键：它告诉 Agent "这不是一个新会话，你在恢复一个已有会话"。没有这句话，Agent 可能把上下文当作"用户输入的一部分"而非"你应该了解的历史"</li><li><b>结构化摘要</b>（如果存在）：SessionMemory 的 renderMemorySummary() 输出。包含 title、status、files 列表（含 path + changeType + description）、errors 列表（分 unsolved 和 solved）、lessons、最近 5 条 workLog。放在最前面是因为摘要提供了宏观认知——Agent 读完这 200-500 字就知道"我们在做什么、进度如何、有什么坑"</li><li><b>提及的 Agent</b>（如果存在）：快照级别的 Agent 列表，与 renderAgentGatewayPrompt 中的 Agent 层是同一份数据，但这里是放在上下文快照内部</li><li><b>body</b>：三个子块的拼接——"## 置顶上下文"（pinned items）、"## 最近对话"（recent messages）、"## 检索上下文"（vector retrieved）。每个子块含多条 "- [kind] text" 格式的条目</li></ol><p>注意 renderContextPrompt 和 renderAgentGatewayPrompt 的关系：renderContextPrompt 的输出被嵌入到 renderAgentGatewayPrompt 的 "## 会话上下文" 段落中。两层嵌套：外层是 AgentHub 编排框架，内层是具体的历史上下文。这形成了 <b>System → Context（含摘要 + Agent + 置顶 + 最近 + 检索）→ Worker Agent → Current Message Context → User Request</b> 的五层结构。</p><h3>一个具体的 Prompt 示例</h3><p>假设用户在主对话中说 "@Claude 帮我把登录按钮改成蓝色"，这是 bootstrap 模式下的完整 Prompt 文本：</p><pre># AgentHub 任务分派 (bootstrap)<br/>请基于以下会话上下文和用户请求完成当前任务。<br/><br/>## 会话上下文<br/>你正在恢复一个已有的 AgentHub 会话。请先阅读以下上下文再执行操作。<br/><br/>## 结构化摘要<br/>任务：电商平台前端开发<br/>状态：进行中<br/>涉及文件：<br/>  - frontend/src/components/Login.tsx (modified) — 登录页面组件<br/>  - frontend/src/styles/theme.css (modified) — 主题样式<br/>未解决的错误：<br/>  - 登录按钮hover效果不生效 → 检查CSS选择器优先级<br/>经验：antd Button 的样式覆盖需要用 :global 或 !important<br/>最近工作：<br/>  - 完成登录页面布局和表单校验<br/><br/>## 提及的 Agent<br/>- Claude (1)<br/>- Codex (2)<br/><br/>## 置顶上下文<br/>- [manual_pin] 我们的设计规范要求主色调为 #1677ff，圆角 6px<br/><br/>## 最近对话<br/>- [message:user] 帮我做一个登录页面<br/>- [message:agent] 已创建 Login.tsx，包含邮箱和密码输入框...<br/>- [message:user] 登录按钮hover效果没生效<br/><br/>## 检索上下文<br/>- [artifact] theme.css 中 .login-btn 的样式定义为...<br/>- [file_change] Login.tsx 修改了 button type 为 primary<br/><br/>## 可用 Worker Agent<br/>- 2: 擅长代码审查和优化<br/><br/>## 当前用户请求<br/>帮我把登录按钮改成蓝色</pre><p>如果是 incremental 模式（用户在 1 小时内发的第二条消息），Prompt 变成：</p><pre># AgentHub 任务分派 (incremental)<br/>请基于以下会话上下文和用户请求完成当前任务。<br/><br/>## 当前用户请求<br/>帮我把登录按钮改成蓝色</pre><p>incremental 模式下 Agent 只收到两段：System 层（标注 incremental）+ 用户请求。因为 Agent 自己的进程内存里有完整上下文——它记得正在做电商项目、改过 Login.tsx、有个 hover 效果的 bug。</p><h3>两个模式的本质区别</h3><p>不只是"省 token"。bootstrap 和 incremental 代表了两种完全不同的上下文传递策略：</p><table><colgroup><col/><col/><col/></colgroup><tbody><tr><td><p></p></td><td><p><b>bootstrap</b></p></td><td><p><b>incremental</b></p></td></tr><tr><td><p><b>上下文来源</b></p></td><td><p>AgentHub 的 ContextSnapshot（数据库+向量检索）</p></td><td><p>下游 Agent 的进程内存</p></td></tr><tr><td><p><b>信息质量</b></p></td><td><p>经过优先级裁剪和语义检索，精准但可能有信息丢失</p></td><td><p>完整对话历史，但没有语义检索增强</p></td></tr><tr><td><p><b>成本</b></p></td><td><p>embedding API + pgvector 查询 + 数万字符传输</p></td><td><p>几乎为零</p></td></tr><tr><td><p><b>适用场景</b></p></td><td><p>新会话、断连恢复、超 1 小时续聊</p></td><td><p>1 小时内连续对话</p></td></tr></tbody></table><p>两种模式互补而非互斥：bootstrap 提供"系统级"的上下文（跨 Agent 实例共享的 SessionMemory + 向量检索），incremental 提供"进程级"的上下文（下游 Agent 自己的精确记忆）。</p><h3>renderContextPrompt 中 body 的排序为什么是 置顶→最近→检索？</h3><p>三个子块的顺序不是随意的。LLM 存在"中间丢失"效应：prompt 中间的信息容易被忽略，开头和结尾的权重更高。因此：</p><ul><li><b>置顶放在最前面</b>：用户手动 pin 的内容是最重要的（显式意图），应该获得最高注意力。放在 body 的第一个块（紧跟在摘要之后），确保不被稀释</li><li><b>最近放在中间</b>：最近 24 条消息信息量大但重要度参差不齐。放在中间位置，既是"填充"也是"背景"</li><li><b>检索放在最后</b>：向量检索的结果是"可能相关"——不是确定性的重要内容。放在最后，即使被 Agent 忽略，损失也最小。而且排在最近消息之后，形成一个"从确定重要到可能相关"的衰减排列</li></ul><p>如果把检索放在最前面（和很多 RAG 系统做的一样），语义相近但可能不重要的旧消息会抢占 Agent 的注意力，稀释最近对话的时效性价值。</p>
