<h2>设计思路</h2><p>会话记忆系统解决的核心问题是：<strong>如何在多轮对话中让 Agent 记住关键上下文，同时不超出 token 限制</strong>。系统采用<strong>三层记忆架构</strong>：短期缓冲（实时事件积累）→ 结构化记忆（LLM 提取 JSON）→ 向量检索（语义召回）。与传统的"全量历史→LLM 总结→长文本"链式方案不同，本系统使用<strong>增量结构化提取</strong>，每次只从新事件中提取增量信息，与已有记忆合并去重。</p><hr/><h2>架构决策</h2><h3>为什么使用增量结构化提取而非全量总结？</h3><p><b>决策</b>：每次达到阈值时，仅将<strong>短期缓冲中的新事件</strong>发送给 LLM，提取结构化字段（title、status、files、errors、lessons、workLog），然后与已有 SessionMemory 记录合并。</p><p><b>理由</b>：</p><ul><li><b>成本控制</b>：每次 LLM 调用只处理 ~2000 tokens 的新事件，而非整个会话历史的数万 tokens。随着会话增长，增量方案的成本是 O(1) 而非 O(n)</li><li><b>信息不丢失</b>：files 按 path 去重、errors 按 message 去重、workLog 追加新条目。不会因为重新总结而丢失早期细节</li><li><b>结构化优势</b>：JSON 结构比自由文本更容易被下游 Prompt 引用和裁剪</li></ul><p><b>为什么不采用更优的 LangChain Memory 方案？</b>LangChain 提供了多种 Memory 类型（ConversationBufferMemory、SummaryMemory 等），但它们都是全量总结模式，随着对话增长总结质量会下降（"中间丢失"问题）。AgentHub 的增量合并方案更适用于长会话场景。</p><h3>为什么短期缓冲阈值设为 20 事件 / 2000 tokens？</h3><p>这是成本和时效性的平衡：</p><ul><li><b>太低（如 5 事件）</b>：频繁调用 LLM 提取记忆，成本高且提取质量差（信息量太少，LLM 容易返回空结果）</li><li><b>太高（如 100 事件）</b>：记忆更新不及时，Agent 在下一次 run 启动时可能缺少最近的上下文</li><li><b>2000 tokens</b>：大约是 1 次 LLM 调用的合理输入量（加上 system prompt 和 max_tokens 800，总 token 在 3000 内，成本约 $0.001）</li></ul><h3>为什么使用 pgvector 余弦距离而非欧氏距离？</h3><p>余弦距离（<=> 运算符）关注向量方向而非绝对大小，适合语义相似度计算。text-embedding-3-small 输出的向量在余弦空间中语义相近的文本方向一致，与距离无关。欧氏距离受向量模长影响，在文本嵌入场景中效果不如余弦距离。</p><hr/><h2>关键数值分析</h2><table><tr><td><p>参数</p></td><td><p>取值</p></td><td><p>分析</p></td></tr><tr><td><p>CONTEXT_TOKEN_BUDGET</p></td><td><p>9000</p></td><td><p>考虑主流模型
