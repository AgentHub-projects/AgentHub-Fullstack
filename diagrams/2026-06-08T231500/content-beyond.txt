<hr/><h2>课题要求超越分析</h2><p>以下分析对比课题原始要求、常规做法和 AgentHub 的实际实现，逐项说明哪些部分超越了课题期望。</p><h3>一、Session Memory 结构化增量记忆系统</h3><table><colgroup><col/><col/><col/></colgroup><tbody><tr><td><p></p></td><td><p><b>课题要求</b></p></td><td><p><b>常规做法</b></p></td><td><p><b>AgentHub 做法</b></p></td></tr><tr><td><p><b>上下文管理</b></p></td><td><p>"聊天历史自动作为上下文传递，支持手动 pin"</p></td><td><p>直接拼接最近 N 条消息作为 context，不做加工</p></td><td><p>三层记忆架构：短期缓冲 → LLM 结构化提取 JSON → pgvector 语义检索</p></td></tr></tbody></table><p><b>为什么超越了：</b></p><ul><li><b>增量 LLM 提取</b>：不是全量重新总结（O(n) 成本），而是每次只从新增的约 2000 tokens 中提取增量字段（title、status、files、errors、lessons、workLog），与已有记录合并去重。成本 O(1)。</li><li><b>结构化 JSON 记忆</b>：files 按 path 去重、errors 按 message 去重、workLog 追加新条目。这让记忆可以按字段裁剪注入 prompt，而非一段无法拆分的文本。</li><li><b>完整的 prompt 注入链</b>：buildSessionMemory() → loadSessionMemorySummary() → renderMemorySummary() → buildSnapshot()，每一步都可独立调试。</li></ul><p>常规做法会在长对话中丢失"中间信息"——第 50 轮的总结覆盖了第 3 轮的关键决策。增量合并方案不存在这个问题。</p><h3>二、pgvector 向量语义检索</h3><table><colgroup><col/><col/><col/></colgroup><tbody><tr><td><p></p></td><td><p><b>课题要求</b></p></td><td><p><b>常规做法</b></p></td><td><p><b>AgentHub 做法</b></p></td></tr><tr><td><p><b>检索</b></p></td><td><p>无（课题只要求历史拼接）</p></td><td><p>无检索，或关键词 grep</p></td><td><p>recallByPgvector()：cosine distance 语义搜索 + 词法回退</p></td></tr></tbody></table><p><b>为什么超越了：</b></p><ul><li><b>自建 embedding pipeline</b>：createEmbedding() → persistEmbedding() → ON CONFLICT DO UPDATE 幂等写入</li><li><b>双层回退</b>：pgvector 如果没迁移或挂了 → 自动切到词法子词匹配</li><li><b>检索结果参与 prompt 优先级排序</b>：置顶项（最高优先级）→ 最近消息（时效性优先级）→ 向量检索（语义优先级），三层预算裁剪</li></ul><p>常规做法是"把聊天记录全扔给 LLM"，这在长会话中会超出 context window。该方案在预算有限时优先保留最相关的信息。</p><h3>三、Prompt 构建的优先级贪婪选择算法</h3><table><colgroup><col/><col/><col/></colgroup><tbody><tr><td><p></p></td><td><p><b>课题要求</b></p></td><td><p><b>常规做法</b></p></td><td><p><b>AgentHub 做法</b></p></td></tr><tr><td><p><b>Prompt 组装</b></p></td><td><p>无具体要求</p></td><td><p>拼接 system + history + user</p></td><td><p>selectWithinBudget() 三轮优先级裁剪 + renderContextPrompt() 分层渲染</p></td></tr></tbody></table><p><b>为什么超越了：</b>selectWithinBudget() 不是简单的"挑前 N 条"——三轮独立预算上限保证了不会因为一条 pin 耗光预算而丢失近期对话，检索结果至少保留 1000 tokens 硬兜底，item.id 去重避免同一条消息重复占用预算。常规做法是一刀切按时间截断，该三层设计反映了对"什么信息对 Agent 最重要"的深刻理解（用户显式置顶 > 时效性 > 语义相关）。</p><h3>四、ACP 协议完整实现</h3><table><colgroup><col/><col/><col/></colgroup><tbody><tr><td><p></p></td><td><p><b>课题要求</b></p></td><td><p><b>常规做法</b></p></td><td><p><b>AgentHub 做法</b></p></td></tr><tr><td><p><b>Agent 接入</b></p></td><td><p>"统一适配器层，接入至少 2 个平台"</p></td><td><p>直接调 CLI 或封一层 REST</p></td><td><p>完整 ACP JSON-RPC 2.0：initialize → session/new → session/prompt → session/update → session/cancel 生命周期</p></td></tr></tbody></table><p><b>为什么超越了：</b>不是"接入了两个平台"，而是实现了一个生产级的 Agent 通信中间件：AcpConnection 完整 JSON-RPC 客户端（id 匹配、超时、错误处理）、DownstreamOrchestratorService 连接池管理（connections Map + DB 持久化 downstreamSessionId + Redis TTL 空闲断开）、session/update 多事件类型各自独立处理路径。新平台接入只需实现 ACP adapter，不用改核心协议。</p><h3>五、事件驱动的流式架构</h3><table><colgroup><col/><col/><col/></colgroup><tbody><tr><td><p></p></td><td><p><b>课题要求</b></p></td><td><p><b>常规做法</b></p></td><td><p><b>AgentHub 做法</b></p></td></tr><tr><td><p><b>实时性</b></p></td><td><p>"IM 核心体验流畅"</p></td><td><p>轮询或简单 WebSocket 透传</p></td><td><p>HubEventService 集中事件总线 → HubRealtimeGateway 实时广播 → 前端 EventStreamBuffer 增量渲染</p></td></tr></tbody></table><p><b>为什么超越了：</b>事件粒度极细——不是"消息完成"时推一次，而是 message.delta（逐块文本）、file.change（文件差异）、artifact.upsert（产物更新）各自独立推送；HubEventService.append() 统一处理副作用，新增事件类型只需加一个 case；前端 EventStreamBuffer 将零散事件组装为时间线视图（思考块 → 消息气泡 → 产物卡片）。</p><hr/><h2>超越总结</h2><table><colgroup><col/><col/><col/></colgroup><tbody><tr><td><p><b>超越部分</b></p></td><td><p><b>超越程度</b></p></td><td><p><b>课题是否要求</b></p></td></tr><tr><td><p>Session Memory 增量结构化提取</p></td><td><p>大幅超越——从"传递历史"升级为"自主构建结构化记忆"</p></td><td><p>否</p></td></tr><tr><td><p>pgvector 语义检索</p></td><td><p>大幅超越——增加了课题不要求的 RAG 基础设施</p></td><td><p>否</p></td></tr><tr><td><p>Prompt 优先级贪婪选择</p></td><td><p>明显超越——从"拼接文本"升级为"预算感知的上下文选择"</p></td><td><p>否</p></td></tr><tr><td><p>ACP 协议完整实现</p></td><td><p>明显超越——从"适配器"升级为"标准协议中间件"</p></td><td><p>部分（适配器层有要求，但协议级远超）</p></td></tr><tr><td><p>事件驱动流式架构</p></td><td><p>适度超越——事件粒度远超常规 IM 聊天</p></td><td><p>部分</p></td></tr></tbody></table><p><b>最有说服力的一点：</b>课题要求的是"让多个 Agent 能对话"，AgentHub 做的是"一个自维护记忆、自检索上下文、自适应 token 预算的 Agent 协作平台"。Session Memory + pgvector + selectWithinBudget 三者组合，形成课题根本没提但实际非常需要的<strong>"零配置智能上下文"能力</strong>——这应该是答辩中最加分的地方。</p>
