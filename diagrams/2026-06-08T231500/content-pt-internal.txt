<hr/><h2>内部 Prompt 的结构化设计</h2><h3>什么是"内部 Prompt"？</h3><p>这里的 Prompt 不是指 HTTP API 的请求体，而是 AgentHub 内部组装、最终注入给下游 Agent 的<b>文本指令</b>。它由 renderAgentGatewayPrompt() 和 renderContextPrompt() 两个函数协作生成，决定了 Agent 看到什么、理解什么、执行什么。这条 Prompt 的质量直接影响 Agent 产出的质量。</p><h3>四层分层结构</h3><p>Prompt 文本被拆成四个逻辑层次，逐层组装：</p><table><colgroup><col/><col/><col/></colgroup><tbody><tr><td><p><b>层次</b></p></td><td><p><b>内容</b></p></td><td><p><b>职责</b></p></td></tr><tr><td><p>System 层</p></td><td><p>"AgentHub 任务分派 (bootstrap/incremental)" + 行为边界说明</p></td><td><p>告诉 Agent <b>你是谁、你在什么框架下运行</b>。bootstrap 和 incremental 两种模式会影响 Agent 的上下文处理策略</p></td></tr><tr><td><p>Context 层</p></td><td><p>ContextSnapshot.promptText：置顶上下文 + 最近对话 + 语义检索结果 + 结构化记忆摘要</p></td><td><p>告诉 Agent <b>之前发生了什么、哪些信息是重要的</b>。这是动态组装的部分，每次 run 可能不同</p></td></tr><tr><td><p>Agent 层</p></td><td><p>提及的 Agent 列表（name + id）+ 可用 Worker Agent（id + description）</p></td><td><p>告诉 Agent <b>你可以和谁协作</b>。Orchestrator 据此判断"哪些子 Agent 适合处理哪些子任务"</p></td></tr><tr><td><p>Message 层</p></td><td><p>用户的当前输入 + messageContext（附件引用、链接预览等）</p></td><td><p>告诉 Agent <b>用户现在想要什么</b>。这是最直接的任务描述</p></td></tr></tbody></table><h3>为什么分成四层而不是一段长文本？</h3><ul><li><b>可测试性</b>：每层可以独立构造和测试。Context 层的内容来自 ContextSnapshot（可单独审计），Agent 层来自 session_agents 表（可单独查），Message 层就是用户输入（无需加工）</li><li><b>可裁剪性</b>：incremental 模式下可以省略 Context 层（因为下游 Agent 已有上下文），bootstrap 模式下必须包含完整 Context 层。分层使得裁剪逻辑清晰——不需要在一段文本中"找出上下文部分然后删除"</li><li><b>可扩展性</b>：未来如果需要在 System 层和 Context 层之间插入一个"项目规则"层，直接在 renderAgentGatewayPrompt 中加一个 section，不影响其他层</li></ul><h3>Context 层的子结构</h3><p>Context 层本身又有四个子块（由 renderContextPrompt 组装），对应 ContextSnapshot 的四类数据源：</p><table><colgroup><col/><col/></colgroup><tbody><tr><td><p><b>子块</b></p></td><td><p><b>为什么单独列出</b></p></td></tr><tr><td><p>结构化摘要 memory</p></td><td><p>SessionMemory 的文本渲染，放在最前面。这是对会话的"宏观理解"——我们在做什么、进度如何。Agent 先读摘要，建立整体认知</p></td></tr><tr><td><p>提及的 Agent 快照内</p></td><td><p>本次 run 涉及的 Agent 列表。Orchestrator 需要知道"用户 @ 了谁"来决定任务分派</p></td></tr><tr><td><p>置顶上下文 pins</p></td><td><p>用户手动 pin 的消息和代码片段。最高优先级的上下文，用户显式标记"这些很重要，每次都带上"</p></td></tr><tr><td><p>最近对话 recent</p></td><td><p>最近 24 条消息。时效性最高的上下文，反映了当前讨论的焦点</p></td></tr><tr><td><p>检索上下文 retrieved</p></td><td><p>pgvector 语义检索的 top-8 结果。语义相关性最高的历史上下文，与当前用户输入最匹配</p></td></tr></tbody></table><h3>渲染顺序的意义</h3><p>renderContextPrompt 的输出顺序不是随意的——摘要（宏观）→ Agent 信息（群聊协作）→ 置顶（显式重要）→ 最近（时效性）→ 检索（语义相关）。这个顺序对应了 LLM 的注意力衰减特性：<b>越靠前的内容，LLM 关注度越高</b>。摘要放在最前面确保 Agent 先建立整体认知，置顶项排在最近消息前面确保用户显式标记的内容不被近期闲聊淹没。</p><h3>bootstrap vs incremental：两种模式的 Prompt 差异</h3><p>这是 renderAgentGatewayPrompt 的关键分支：</p><ul><li><b>bootstrap 模式</b>（新会话 / 断连后首次）：传入完整 contextText（ContextSnapshot.promptText）和 agents 列表。Prompt 包含全部四层。这是"冷启动"场景——Agent 需要从头理解整个上下文</li><li><b>incremental 模式</b>（1 小时内续发消息）：contextText 为 undefined，agents 为空数组。Prompt 只包含 System 层（标注 incremental）+ Message 层。下游 Agent 已经持有完整上下文，AgentHub 不需要重复发送</li></ul><p>这个分支不止是优化（省 token），更是对<b>"谁在维护上下文"</b>这一职责的清晰划分：bootstrap 时 AgentHub 负责，incremental 时下游 Agent 负责。不是在两个地方同时维护然后试图保持同步（那会引入一致性问题），而是<b>同一时刻只有一方负责</b>。</p><p>注意 renderAgentGatewayPrompt 中 "## Current Message Context" 独立于 ContextSnapshot——这是当前消息携带的结构化元数据（附件引用、链接预览），不是历史上下文。无论 bootstrap 还是 incremental，它都会被包含，因为它属于"当前消息"而非"历史上下文"。</p>
