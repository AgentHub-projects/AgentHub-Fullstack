<hr/><h2>一小时空闲断连的设计缘由</h2><h3>核心决策</h3><p>DownstreamOrchestratorService 在 session 无活跃 run 且无前端订阅时，等待 IDLE_TIMEOUT_SECONDS（3600s = 1小时）后断开下游 WebSocket 连接。</p><h3>一小时内：让底层 Agent 自己维护上下文</h3><p>这是设计的核心思想。AgentHub 的下游是 Claude Code CLI / OpenCode 等 Agent 实例，它们自身就是完整的 AI Agent，有自己的对话记忆和上下文管理能力。</p><p><b>1 小时内的策略</b>：AgentHub 不干预下游 Agent 的上下文维护。连接保持，incremental 模式发送新消息——只传用户当前输入，不重新构建和发送完整上下文快照。下游 Agent 在自己的进程内存中维护对话历史、KV Cache 和工作状态。</p><p>这带来了两个关键收益：</p><ul><li><b>零上下文传输成本</b>：不需要重新构建 ContextSnapshot、不需要重新调用 embedding API、不需要重新查询 pgvector。用户的后续消息直接透传，下游 Agent 自己知道之前发生了什么</li><li><b>零 prefill 成本</b>：下游 Agent 连接的 LLM 推理引擎（vLLM/SGLang）在 1 小时内通常仍持有 KV Cache。新消息作为 decode 阶段的增量输入，不需要重新 prefill 整个上下文前缀</li></ul><p>换句话说：<b>1 小时是"信任下游 Agent 自己能管好上下文"的时间窗口</b>。AgentHub 在这个窗口内退居为消息路由层，不做重复工作。</p><h3>超过一小时：为什么不再信任？</h3><p>超过 1 小时后，两个条件同时失效：</p><ul><li><b>下游 Agent 的进程内存不可靠</b>：1 小时的空闲足够操作系统将进程换出、Claude Code 可能超时退出、OpenCode 可能主动回收空闲 session</li><li><b>LLM KV Cache 必然过期</b>：主流推理引擎的 KV Cache TTL 上限约 1 小时。超过后即使进程还在，下一次推理请求也会触发完整 prefill——下游 Agent 的"免费上下文维护"已经失效</li></ul><p>此时 AgentHub 必须接管上下文管理：断开旧连接 → 创建新连接 → bootstrap 模式 → 重新构建完整 ContextSnapshot（从 pgvector 检索 + 加载 SessionMemory + 收集置顶项）→ 完整发送给下游。既然 KV Cache 已经过期、prefill 成本无法避免，不如让 AgentHub 来构建更精准的上下文（经过优先级裁剪和向量检索），而不是依赖下游 Agent 不完整的记忆。</p><h3>用一个比喻来理解</h3><p>把下游 Agent 想象成一个员工，AgentHub 是项目经理：</p><ul><li><b>1 小时内</b>：员工刚做完上一个任务，手头还有所有资料（KV Cache），记忆清晰（进程内存）。项目经理只需说"继续做 X"，不需要重新交代背景。效率最高。</li><li><b>超过 1 小时</b>：员工去开了个长会回来（进程可能已挂），桌上的资料被清空了（KV Cache 过期）。项目经理需要重新交代完整背景（bootstrap），但这个背景是由 AgentHub 精心整理过的（向量检索 + 记忆摘要 + 置顶项），比员工自己回忆更准确。</li></ul><h3>为什么不一直用 bootstrap 模式？</h3><p>每次都用 bootstrap 模式（完整上下文快照）对 AgentHub 侧最省事——不需要判断"是否在 1 小时内"。但代价很高：</p><ul><li>每次发送消息都要调用 embedding API 做向量检索</li><li>每次都要查询 pgvector、加载 SessionMemory、执行 selectWithinBudget</li><li>每次都要把可能数万 tokens 的上下文快照传输给下游</li><li>下游 Agent 每次都要处理完整的上下文前缀，失去了 KV Cache 复用的机会</li></ul><p>incremental 模式把上下文维护的职责交给下游 Agent（1 小时内它能做得更好更省），bootstrap 模式在 Agent 不可靠时由 AgentHub 兜底。这是<b>职责分离</b>的设计思想。</p>
