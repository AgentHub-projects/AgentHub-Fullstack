<hr/><h2>Prompt 结构化字段的设计意图</h2><h3>为什么每个字段是这样设计的？</h3><p>buildPromptInput() 构造的 ACP session/prompt 参数包含多个字段，每个都有明确的架构意图：</p><table><colgroup><col/><col/><col/></colgroup><tbody><tr><td><p><b>字段</b></p></td><td><p><b>设计意图</b></p></td><td><p><b>为什么不是可选字段</b></p></td></tr><tr><td><p>sessionId</p></td><td><p>复用已有下游 session，避免每次 run 都创建新 session。ACP 协议要求 session/load 或 session/new 后持有 sessionId</p></td><td><p>同一会话内的多次 run 共享同一个下游 session，下游 Agent 可以通过 sessionId 维护自己的内存状态和 KV Cache</p></td></tr><tr><td><p>prompt[] (数组)</p></td><td><p>ACP 标准要求 prompt 为 content part 数组，每个 part 有 type（当前为 text）。数组结构为未来扩展多模态 prompt（如 image part、file part）预留空间</p></td><td><p>单个 text 字符串无法表达多模态输入。数组结构是 ACP 规范要求，也是未来兼容性的保证</p></td></tr><tr><td><p>_meta.source</p></td><td><p>标识请求来源（"agenthub"）。下游 Agent 可以通过 source 判断请求来自哪个平台，用于日志、审计和降级策略</p></td><td><p>未来如果下游服务被多个平台共享，source 是区分流量的关键</p></td></tr><tr><td><p>_meta.agentId</p></td><td><p>当前 orchestrator Agent 的 ID。下游需要知道"谁在给我发指令"，用于 Agent 间的身份识别和权限控制</p></td><td><p>群聊模式下多个 Agent 可能互发请求，agentId 防止身份混淆</p></td></tr><tr><td><p>_meta.agenthubSessionId</p></td><td><p>AgentHub 侧的 session ID。下游事件回调时通过此字段关联回 AgentHub 的 session</p></td><td><p>ACP 协议的 sessionId 是下游侧的，AgentHub 需要自己的 sessionId 来路由回调和更新数据库</p></td></tr><tr><td><p>_meta.runId</p></td><td><p>当前 run 的 ID。下游事件（session/update）回传 runId，AgentHub 据此将事件关联到正确的 run</p></td><td><p>同一 session 内可能有多个 run（如用户连续发两条消息），runId 确保事件不会错配到错误的 run</p></td></tr><tr><td><p>_meta.messageId</p></td><td><p>触发此 run 的用户消息 ID。用于在 UI 中将 Agent 回复关联到正确的用户消息（实现"回复"引用）</p></td><td><p>IM 的引用回复体验依赖于消息关联，messageId 是实现此功能的基础</p></td></tr><tr><td><p>_meta.orchestratorAgentId</p></td><td><p>与 agentId 相同，显式标注 orchestrator 身份。在某些流程中 orchestrator 可能与 speaker 不同</p></td><td><p>当 orchestrator 将任务分派给子 Agent 时，orchestratorAgentId 保持不变，让下游知道"总指挥是谁"</p></td></tr><tr><td><p>_meta.mentionedAgentIds</p></td><td><p>用户在消息中 @ 的 Agent ID 列表。Orchestrator 据此判断哪些 Agent 需要参与当前任务</p></td><td><p>这是群聊模式下任务分派的核心输入——orchestrator 根据 mentionedAgentIds 决定拆分和分派策略</p></td></tr><tr><td><p>_meta.contextSnapshotId</p></td><td><p>关联的 ContextSnapshot 数据库 ID。用于审计——可以追溯"这次 run 用了哪个快照、快照里有什么"</p></td><td><p>调试时可以通过 contextSnapshotId 查到完整的上下文快照内容，判断 Agent 的回复是否受到错误的上下文影响</p></td></tr></tbody></table><h3>为什么 _meta 字段单独一层而不放在顶层？</h3><p>ACP 协议定义的标准字段（sessionId、prompt）和 AgentHub 内部字段（runId、messageId、contextSnapshotId）通过命名空间分离：</p><ul><li><b>不污染 ACP 标准</b>：如果 AgentHub 的内部字段放在顶层，会与未来 ACP 协议新增的标准字段冲突</li><li><b>下游可安全忽略</b>：下游 Agent 可以完全不解析 _meta，只关注 ACP 标准字段。这保证了与标准 ACP 客户端的兼容性</li><li><b>可扩展</b>：未来新增内部字段（如 _meta.priority、_meta.deadline）只需加到 _meta 下，不影响现有逻辑</li></ul><h3>为什么 promptText 要包一层 renderAgentGatewayPrompt？</h3><p>直接发送用户的原始 input 给下游 Agent 是不够的。renderAgentGatewayPrompt() 在用户的 promptText 外面包装了：</p><ul><li><b>AgentHub 任务分派头部</b>：告诉下游 Agent "你是作为 AgentHub 的 worker 在运行，请基于上下文完成任务"。没有这个头部，下游 Agent 可能不知道自己的角色</li><li><b>可用 Worker Agent 列表</b>：让 orchestrator 知道可以调用哪些子 Agent。没有这个信息，orchestrator 无法进行多 Agent 任务分派</li><li><b>上下文快照文本</b>：bootstrap 模式下注入完整的 ContextSnapshot.promptText</li></ul><p>这种包装层的设计使得<b>用户的原始输入</b>和<b>系统的编排指令</b>清晰分离——用户可以自由写任何内容，系统负责在合适的时机注入合适的上下文。</p>
